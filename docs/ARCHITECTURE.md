# Project structure

Tomatoes is a local test report dashboard for reports generated by Cypress tooling. It uses a React component frontend, an esbuild client build, and a Node.js HTTP/API server. Vercel serves the generated static assets and the API function.

```text
tomatoes/
|-- src/
|   |-- client/
|   |   |-- react/          React entry, JSX components and controller adapters
|   |   |-- app.js          Active report, filter and navigation controller
|   |   `-- *.js            Imports, history actions, feature controllers and worker
|   |-- shared/             Report parsing, validation and reusable models
|   `-- server/             Node HTTP/API runtime, storage and SQL migrations
|-- api/server.js           Vercel function entry
|-- public/
|   |-- index.html          React root, appearance bootstrap and styles
|   |-- css/                Base and feature styles
|   `-- assets/             Logo and licensed PDF font
|-- tests/
|   |-- unit/               Models, React interactions and configuration checks
|   `-- integration/        Local HTTP workflows and PostgreSQL checks
|-- scripts/
|   |-- build.js            Public deployment assets and manifest
|   |-- build-react.js      JSX/React bundle compilation
|   `-- *.js                Database, account, CI and verification commands
|-- examples/reports/       Bundled sample report
|-- docs/                   Architecture, integration guides and media
`-- dist/                   Generated Vercel static assets (ignored)
```

## Browser and shared code

`src/client/app.js` coordinates the active report and navigation. The other client modules own history, analytics, investigations, team access, report detail views, workspace tools, custom dashboard widgets and PDF export. `custom-widgets.js` manages the group settings editor; `preferences.js` loads and saves account-scoped server preferences; the shared `dashboard-groups.js` validates group definitions and calculates results from matching spec paths. `report-worker.js` validates and processes imports off the main browser thread.

`src/shared/` contains modules that work in both the browser and Node.js. These hold report normalization, investigation models, attachment validation, Markdown export, PDF document generation, backup validation and history analysis. Keep browser DOM interactions in `src/client/` so shared logic can be tested without a page.

`report-navigation.js` keeps the active import ID in the URL query string while hash navigation selects the view. The shared `report-links.js` validates link IDs and resolves browser copies before attempting a linked, authorized server copy. Direct links take precedence over the browser's last-active report. Missing or trashed imports show an error instead of falling back to another run.

`public/index.html` contains the React mount point and loads `/js/react-app.js`. The appearance bootstrap runs before the styles. `scripts/build-react.js` compiles `src/client/react/main.jsx` and its JSX components into a browser bundle; `scripts/build.js` copies that bundle and the whitelisted public assets into `dist/`. Local startup builds the bundle before starting the server. Build tools and the React dependency are never loaded from a CDN.

React owns the stable shell, navigation markup, dialogs, auth forms, latest-run dashboard widgets, result rows and saved-import cards. Auth forms use React state for validation, pending status, errors and feedback. Dashboard and row actions use React event handlers; imported strings render as text. `report-bridge.jsx` caches separate React roots for dynamic report hosts so updates do not replace the surrounding shell.

`src/client/react/runtime.js` starts compatibility controllers only after the shell commits. The order is explicit in `runtime-scripts.js`, with shared browser models before feature controllers and `app.js` last. Remaining settings, project, users, integrations, investigations and PDF presenters retain their existing DOM rendering in isolated feature hosts. Do not overwrite React-owned roots with `innerHTML`, and do not rerender the stable shell around controller-managed nodes. Compatibility modules initialize DOM listeners immediately when loaded after `DOMContentLoaded`.

When adding a compatibility module, register its URL in `src/server/static-assets.js` and put it in the correct adapter load order. New React components should be imported through the React entry tree. Never add private server modules to the public mapping.

## Server and persistence

`src/server/index.js` starts the loopback HTTP server and delegates team/report API requests to `team-service.js`. `config.js` resolves paths from the repository root, so moving source files does not relocate `.env.local` or `.tomatoes-data`.

`slack-notifier.js` builds Slack messages from normalized saved reports and sends webhook requests on the server. The browser calls `POST /api/runs/:id/slack-notification` only after an import finishes. Environment configuration remains private, and normal project, role, origin and CSRF checks protect the endpoint. Tests inject mock delivery clients rather than contacting Slack.

`storage/index.js` chooses the configured store. `file-store.js` and `postgres-store.js` implement the same storage interface. `json-store.js` handles safe JSON file writes. PostgreSQL schema setup lives in `database/schema.js`, with the initial schema in `database/migrations/001-initial.sql` and user preferences in `002-user-preferences.sql`. The SQL uses a validated schema placeholder and records its applied version. Future schema changes need a new versioned SQL file and an explicit migration runner step; do not rewrite an already applied version to change existing databases.

Time zone, page size and dashboard group definitions use `/api/preferences` and the selected server store. The server derives the preference owner from the authenticated session, or uses one shared `local` profile without sign-in. Preference updates require same-origin requests and session CSRF tokens, and CI tokens are excluded. Existing browser preferences are imported only when the shared local profile is empty.

Browser history stays in IndexedDB. Server copies use the selected server store. In PostgreSQL mode, report JSON, account records, sessions, rate limits, preferences and new attachment bytes live in the database. Legacy attachment records may still refer to `.tomatoes-data/attachments`; keep those files until their bytes have been migrated. File-store mode uses the local attachment directory. `.env.local` and `.tomatoes-data` remain private, ignored files at the repository root.

## Development commands

- `npm start`: build the React bundle and start the application at `http://localhost:3000`.
- `npm run build` / `npm run build:production`: compile JSX and prepare static assets, with the latter also running syntax checks and tests.
- `npm run check`: check JavaScript syntax throughout source, scripts and tests.
- `npm test`: run unit tests and local integration workflows.
- `npm run test:postgres`: run live database tests in isolated temporary schemas.
- `npm run format` / `npm run format:check`: apply or check Prettier formatting.
- `npm run db:check`: verify the configured database connection without changing data.
- `npm run db:migrate`: apply the database schema.
- `npm run db:import-files`: copy existing file-store records into PostgreSQL.
- `npm run team:admin -- <arguments>`: manage local accounts or CI tokens.
- `npm run report:publish -- <arguments>`: publish a report from local CI.

Place new tests under `tests/unit/` for automatic discovery. Add local integration suites to `scripts/test.js`; database suites run separately to keep normal tests independent of PostgreSQL. The syntax checker discovers JavaScript recursively under `src/`, `scripts/` and `tests/`.

See the [README](../README.md) for setup, report features and publishing examples.

## Project directory

`src/shared/project-management.js` validates shared project names and stable project identifiers. `/api/projects` lists projects visible in the caller's scope. POST creates a project; PATCH `/api/projects/:id` changes its display name. Only global admins can mutate the directory, with origin and CSRF validation; CI tokens are excluded. The registry is shared by the configured installation rather than stored in per-user preferences.

Migration `006-projects.sql` adds the PostgreSQL registry. Both stores merge registry entries with project identifiers discovered from existing server runs. Directory updates serialize duplicate-name checks (a store queue for files, an advisory transaction lock for PostgreSQL). Renaming updates the registry only and leaves all report JSON, identifiers, project scopes, branches and archive metadata intact. The Projects catalog also includes empty registered projects and browser imports. React's project editor handles pending state, errors and repeated creation. `import-projects.js` fills the project picker and refreshes branch options when selection changes.

User membership is explicit in migration `007-user-organization.sql` (`organization_id`, default `default`). Legacy file-store users without the field belong to the configured installation. Sessions, sign-in, recovery and user administration reject foreign membership; the current API does not implement multiple organizations in one installation. User project assignments must exist in the installation directory, which also discovers legacy assigned scopes. The React project picker submits stable identifiers and requires an explicit all-project choice. Shared `project-access.js` also filters browser history, evidence and backups by the authenticated account; server APIs remain the authority for stored reports. Navigation refreshes the principal and clears inaccessible reports and derived caches before restoring a local report.
